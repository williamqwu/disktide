# Changelog

## Unreleased

**A scanner that reads a whole directory in one GIL release, a scan that stopped spending a quarter of itself in the garbage collector, a scheduler that applies each directory once instead of twice, a live scan paced by what the screen actually draws, a progress overlay that stopped repainting for the whole of a scan, a key map that exists, a command palette that was switched off, a footer that fits the terminal it is drawn in, nine keys that stopped meaning two things, and a UI a browser terminal can measure**

- **eight scan workers were slower than one, and the reason was the GIL rather than the disk** Every `DirEntry.stat` releases the interpreter lock for its `fstatat` and takes it back afterwards, so a scan of the 88,000-directory fixture made about 976,000 handoffs -- one per entry -- and each of them queued the worker behind whatever else wanted the lock. With a busy scheduler thread that is up to the 5 ms switch interval per entry, which is how eight workers on a warm local tree came to finish *slower* than one: raw 1w 13.2 s against raw 8w 22.5-24.1 s, of which 17-18 s was system time. `disktide/scanner/_scanfast.c` reads a whole directory -- `fdopendir`, the `readdir` loop, and an `fstatat(AT_SYMLINK_NOFOLLOW)` for every entry that is not a directory -- inside one `Py_BEGIN_ALLOW_THREADS`, and hands back a list of ten-field tuples. 88,000 handoffs instead of 976,000. Medians of three interleaved reps on the 976,100-entry fixture (87,999 dirs / 888,100 files, warm xfs), against this branch's base, at host load 73:

  | fixture, mode | base | native | pure-Python fallback |
  |---|---|---|---|
  | raw 1w | 8.82 s (u 5.9 / s 3.1) | 8.03 s (u 5.2 / s 3.0) | 8.83 s |
  | raw 8w | 18.15 s (u 14.0 / **s 18.0**) | **8.36 s** (u 6.5 / s 4.9) | 19.10 s |
  | live 1w | 10.57 s | 9.49 s | 10.75 s |
  | live 8w | 20.53 s (s 18.4) | **9.73 s** (s 5.0) | 20.72 s |

  Read the system-time column: eight workers spent 18 s of it fighting for the lock, and 5 s once the fight was over. And read the base row twice -- eight workers were *twice as slow* as one, which is what a convoy looks like from outside. In the real TUI at 307x69 the same shape holds: live-off 8w 18.46 s -> 8.92 s, live-on 8w 22.44 s -> 11.18 s, and the CPU actually spent on the walk drops from 31.3 s to 11.8 s because most of it was never walking. One worker gains about 8-10 % in every mode; eight gain 2.1x. What the walk gives up for it is granularity inside one directory: a read of a 300,000-entry directory is about 0.3 s and is not interruptible, so a cancel lands after it rather than during it. Ordinary directories are microseconds and the chunking is untouched -- the read is whole-directory, the flush is still every 256 entries, so a live scan of an enormous directory updates exactly as often as it did.

- **the extension is optional, and nothing about disktide's dependencies changed** `disktide/scanner/accel.py` picks a reader once, at import: the C one where it was built for the running interpreter, `_scanfast_py.py` -- the same work through `os.scandir(fd)` -- everywhere else. There is one entry loop in the scheduler, not two, and it consumes tuples either backend produces, which is why the trees are byte-identical: `tool/dump_tree.py --backend native|python` on the 976,100-node fixture at one and eight workers, and against the pre-change build, differs in nothing. `pip install disktide` and `uv tool install disktide` get a prebuilt wheel with the extension in it on Linux and macOS; anywhere else they get the source distribution, which compiles it if a compiler is there and installs the fallback, without an error, if not. `disktide doctor` prints which one is live (`Scanner: native (_scanfast)` / `Scanner: python fallback (...)`), `doctor --json` carries it under `platform.scanner` (schema 6 -> 7, with `application.core_install` now reading `native-accelerated` or `pure-python` rather than always the latter), `tool/bench_scan.py --json` records it next to every timing, and `DISKTIDE_ACCEL=0` forces the fallback for one run. What the fallback loses is speed, and nothing else.

- **a quarter of every scan was the garbage collector looking for cycles in a tree that has none** A scan builds about a million objects the cyclic collector tracks -- one node per file, one node and one child list per directory -- and every one of them points downward only. So each full collection walked the whole tree to find nothing, and did it again every time the allocation counter crossed its threshold: nine times in a raw scan of an 88,000-directory tree, twelve in a live one. Measured against the same scans with the collector switched off, that is **22 % of a raw scan and 30 % of a live one**. Two rounds of py-spy had missed it and could not have found it -- a collection runs inside whichever allocation happened to trigger it, so its time is charged to the scanner's own frames, which is exactly why the last two rounds of this work blamed the publish path. `gc.callbacks` is what sees it, and `tool/bench_scan.py --json` reports a `gc` object now so the next regression is visible. The walk switches the collector off for its duration and puts it back on every exit it has, including a cancelled scan and one that raises; and because a paused walk leaves everything it built in the young generation, where the first collection afterwards would walk all of it, the finished tree is collected once on the way out and then `gc.freeze()`d into the permanent generation, which no later collection walks at all. That second half is what a resident tree costs when it is *not* being scanned: a full collection with the fixture's tree loaded is a 720-770 ms pause on whatever thread Python decides to run it on, and after the freeze it does not happen at all. Getting that right took two goes and a memory soak in the real TUI, because the tree being acyclic is necessary and not sufficient: what *holds* it behind the explorer is a Textual widget graph that is full of cycles, and pinning those meant they were never collected once they became garbage. Three rescans of the fixture went 654 MB, 1251, 1847, 2440 and climbing. Handing the previous freeze back at the next one bounded it, at 1245, 1703, 1700 -- still a whole tree above the base, because the rows that held the last scan's frames only become garbage when the screen swaps in the final tree, which is *after* the walk has frozen them. Reclaiming that with a collection after every completion worked and cost 2.2 to 2.8 s of stop-the-world at the exact moment a user has just got their answer, so it is not what shipped. What ships is letting go of the tree explicitly, in the three places that were still holding it: every row the size tree had drawn (`Tree.clear()` does not delete rows, it stops referring to them, and a row graph is cyclic, so the old rows survive as an island still holding the nodes they were drawn from), the finished `ScanRun.root`, and the category rollup's worker argument -- Textual keeps a worker's arguments for the life of the worker record, so a tree passed to one positionally is still referenced long after the pass that used it. Each is now dropped by assignment the moment it goes stale, the refcount reaches zero on the spot, and there is no pause at all: three rescans of the fixture sit at 1069, 1123 and 1165 MB against a base at 1261, 1273, 1263 -- 8 % *below* the revision that never froze anything. And the first freeze of a process now collects nothing -- there is nothing pinned yet and the walk's own objects are acyclic, so it was 0.7 to 1.3 s that `disktide scan` paid on its way out and got nothing for. None of this is safe unless the node graph really is acyclic, so that is a test rather than an assertion -- `tests/test_gc_floor.py` drops a scanned tree and checks that refcounting alone freed every node before any collection ran, for `FSNode`, `LeafNode`, `LiveViewNode` and the scheduler's `_DirectoryState`, and checks that a *frozen* tree is still freed when the next scan replaces it. If one of them ever grows a back-reference the test fails, rather than `watch` leaking a tree a day.
- **a live scan stopped building frames nobody looks at** A live scan publishes a tree checkpoint every 0.25 s, and the explorer applies exactly one of them: the newest, and only when its UI-duty loop opens, which on a 307x69 terminal is every 0.4 to 2.5 s. Every other frame was built, handed over, and dropped -- and a frame is not free once it is out, because the generation bump behind it makes the next write into any directory chain clone that chain's spine so the frame stays immutable. So a frame nobody reads is paid for twice, once to build and once in the clones it forces on the walk behind it. A frame now carries an `ack`, the consumer calls it when it has *applied* the frame, and the scheduler builds no further non-forced frame until then: 53 frames became 28 on an 88,000-directory tree at one worker, 95 became 49 at eight. Forced publishes -- a depth-0 completion, an entry-chunk checkpoint -- and the one frame of credit each leaves behind are never held back, so a scan that finishes inside one window still shows something before it shows everything; a consumer that acknowledges nothing (the events-only service path, a headless bench, a future web UI) is fed on a cap of eight callback intervals, counted in intervals rather than seconds so that `tree_callback_interval=0.0` still means what it says. Two things every publish did for nobody are gone with it: the changed-directory list was sorted by (depth, path) although the one consumer that cares re-sorts the handful of rows it can draw, and the settled-path set was copied into a `frozenset` that nothing reads. py-spy has `_publish_tree` at 1.3 % of the scheduler thread against 6.1 %. And `SizeTree.apply_live_update` filters to the rows it has actually materialised before it sorts, which is dozens rather than thousands.
- **the progress overlay was repainting the whole screen to draw a band that never moves** The one number a user watches during a scan was called cheap per event, and per event it is. Per scan it was not: `ScanProgressUpdated` arrives at up to 20 Hz and each one dirtied three widgets, and underneath them Textual's indeterminate `Bar` arms `auto_refresh = 1/15` to animate its band -- except that this app runs at `animation_level = "none"`, where `Bar.render_indeterminate` returns the identical full-width band on every frame. Fifteen compositor passes a second, for the length of a scan, to redraw the same strip. Every thread in the process shares one GIL, so none of that was spare capacity; it was the walk not running. Measured in the real TUI at 307x69 with the live chart switched off entirely, the UI thread spent 1.15 s of a 15.2 s scan on the two of them. The overlay keeps the newest report and redraws from one 5 Hz timer -- flushing at once on the first report of a scan and on completion, cancellation or failure, so the last numbers are never stranded -- and clears the bar's timer: **0.42 s**, and the whole scan 15.0 s. In the TUI with live rendering *on*, 21.5 s to 19.9 s.
- **the first live frame of a scan could be held back for minutes on a young host** The live UI's duty gate opened a scan by stamping its two clocks at zero and letting the debt formula decide, which only works while the thread's whole CPU history times the duty ratio is smaller than the host's uptime. On a developer's node that is seconds against weeks; on a CI runner booted five minutes earlier, inside a test worker with two minutes of CPU behind it, the first frame was deferred by eleven minutes -- and a fresh container on a rescan can get there too. The open gate is now a state of its own, and the window starts at the frame it lets through.
- **a symlink four thousand characters deep was reported broken** The scan has walked past PATH_MAX since `open_scan_directory` learned to open a path in chunks, but `classify_symlink` still asked `os.readlink(path)` and `os.stat(path)`, and a syscall's pathname argument is capped at 4,096 bytes on Linux. So at the bottom of a deep tree both raised ENAMETOOLONG, the readlink was swallowed and the stat was read as "target unresolvable": a perfectly good link, shown broken, with no target -- the question could not be asked and the answer was reported anyway. Past 4,000 characters it opens the parent and asks about one name under that descriptor. The cleanup path was audited for the same failure and deliberately not changed: it names whole paths in five places and only its machinery below an already-opened parent is descriptor-relative, so a deep row refuses to be deleted rather than being deleted wrongly, which is the right side to fail on and is now pinned by a test.
- **what is left is the garbage collector, and it is bigger than any of this** The live-rendering bullet further down said the floor under a live scan was the copy-on-write publishing, and that it was the next thing to look at. It is not, or not mostly. Measuring GC pause time directly on the 88,000-directory fixture at one worker: a raw scan spends **3.49 s** in collection (9 full passes, 2.84 s of them) of a 13.2 s wall clock, and a live scan **6.05 s** (12 full passes, 4.90 s) of 17.2 s. Running the same two scans with the collector switched off gives 10.0 s and 11.7 s -- so 26 % of a raw scan and 35 % of a live one is the collector walking a heap of about a million `LeafNode`s, `FSNode`s and their child lists looking for cycles in a tree that has none, and 2.6 s of the 4.3 s live-over-raw gap is that walk being longer and more frequent rather than anything the publish path does. The copy-on-write clones are real but small: removing every one of them, and the final whole-tree clone with them, takes a live scan from 17.0 s to 16.2 s. Nothing in this release changes a GC setting -- it is process-wide, and a Textual app that disables collection for the length of a scan is a decision that wants its own soak test -- but that is where the next second is.
- **the two directory readers disagreed about an invalid descriptor** `scan_dir(-1)` raised `EBADF` from the extension, which dups the descriptor before `fdopendir`, and listed the *current working directory* from the pure-Python fallback, because `os.scandir(-1)` is `AT_FDCWD`. Nothing reaches either of them with a negative descriptor today -- `scan_directory_once` keeps `-1` as its "the open failed" sentinel and returns before the read -- so this is hardening rather than a live bug. But the fallback exists to be tuple for tuple the same function, and of the two answers to "read the directory on this descriptor" only one of them is an answer. Found by a stress harness that counted 1,200 `OSError`s from one reader and none at all from the other over the same 1,200 calls.
- **a database from a newer disktide opened in silence, and an old one was emptied without a copy** Two failures in `storage/migrations.py`, and both are the version stamp being trusted further than it can be. `get_version` answers 0 for every way of failing to read `schema_version` -- the table dropped, the file half written -- and 0 is also what a database created a microsecond ago says, so `_create_backup` skipped the copy in exactly the case where it is worth most: a v1 or v2 file whose stamp is unreadable replays the whole chain, and migration 3 drops `nodes` and deletes every snapshot and alert event. Measured before the change, from a v1 and a v2 database each holding one snapshot: `snapshots 1 -> 0, backup=None, version_now=10` -- nothing to restore from, and no second chance, because the stamp now reads 10. The backup is decided from `sqlite_master` instead: anything holding a user table gets copied first, and a brand-new file still gets nothing. In the other direction `migrate` read `current >= target` as "nothing to do", so a file written by a *newer* disktide opened cleanly and was then written through a schema this build only half understands -- added columns carry defaults, so most of it appears to work, and what is left is a column whose meaning changed being read as though it had not. It raises `SchemaTooNewError` now, a `sqlite3.DatabaseError` so the read-only fallback `Database.connect` already has picks it up without a second mechanism: history stays readable, nothing new is written, `doctor` prints `Schema: 99 / 10 (newer than this build)` and a hint that names the fix, and `disktide scan --snapshot` exits non-zero instead of reporting a save that did not happen.
- **stopping continuous sampling left the monitor reading "waiting" against a host that was gone** The monitor screen stops the host with `stop_session(wait=False)`, because it cannot hold the UI thread for a ten-second join -- so `_release_all_leases` runs beside a session thread still inside a loop iteration it entered before the stop flag went up. `_acquire_session_lease` was the one writer of `WAITING` that never asked whether the host was stopping, and a lease taken in that window is one nothing releases afterwards: the release has already cleared `_held_leases`, the session loop's own `finally` finds it empty, and the `WAITING` written after it is the last word. The button went back to "Start sampling" and the row kept saying *waiting*, against a host id whose process had exited, until the lease expired and `_normalized_status` cleared it. CI caught it once, in one job of nine, on a two-core runner; it is pinned now by suspending the session thread between taking the lease and writing the status that goes with it. The guard is asked *after* that write rather than before it, because the write is the thing that has to be undone.
- **and the same defect had a second writer: a monitor status row is edited by four threads, and whoever saved last won** `MonitorService` persists status by `get_monitor_status` -> edit fields -> `save_monitor_status`, from the session loop, the event backend's callback thread, the scan-event consumer, and whichever thread calls `stop_session`. Nothing ordered them, so a write landing between another thread's read and its save was simply dropped. The visible one: a backend failure falls back to periodic while the run that follows it is mid-finish, and the finish's save carries its pre-fallback copy -- event-assisted/active -- back over the fallback; because `_finish_full_reconciliation_status` reads `event_backend_status` to decide whether the backend failed, the row then says "active" for good with no backend behind it. That was 1 test of 1,888 red in the Python 3.10 CI job on 593a527, against 96/96 green locally on a 16-core box; the wave06 stop-path failure above came back twice from the same cause, on a different writer. A `_status_lock` `RLock` now covers every read-modify-write of a status row, and `release_monitor_lease` -- which writes `activity_state='no-host'` itself -- under the same acquisition as the backend-stopped write beside it, so a finishing run cannot decide "still hosted" and save that on top of a release. The lock deliberately excludes what would deadlock or stall behind it: `backend.stop()` (it joins a watcher thread that may itself be waiting for the lock), backend starts, scans, joins, condition waits, and `_emit` (consumers are arbitrary callables). Order is `_status_lock` then `_condition`, never the reverse. `stop_session(wait=False)` on the UI thread can now wait for one locked region -- milliseconds, with no scan inside it.
- **the same build, the same tree and the same theme looked like a different application in a web shell** In Open OnDemand's browser terminal the header border and the footer were solid purple, the inner ring and both the `archive` and `ephemeral` wedges were one hot pink, `data` was the same purple as the border, and on the highlighted row the size text was simply not there -- the bar and the percentage were, the number was not. Nothing was wrong with the palette. OnDemand spawns its pty with `TERM=xterm-16color`, so the tmux client attached from it reports `client_termfeatures = bpaste,ccolour,clipboard,cstyle,focus,title` with no `256` and no `RGB`; inside tmux the app sees `TERM=tmux-256color`, believes it, and writes 256-colour SGRs that tmux maps through its own static `colour_256to16` table before the browser sees any of them. Modelling the whole window through that pipeline: 39 distinct colours at 24-bit, 30 after Rich's match to the xterm-256 cube, **13** after tmux's table. `archive`, `ephemeral` and the neutral directory ring all arrive as ANSI 1, which xterm.js's Monokai Remastered paints hot pink; `data`, `$primary`, `$border` and the block cursor all arrive as 12. The missing size text is the same bug in text: it is styled `dim`, `dim` names no colour, and a browser renders that by blending toward whatever is behind it -- which on the cursor row was the selection bar. JupyterLab's terminal is the same story with `TERM=xterm-color`, which Rich also reads as sixteen because the suffix is not in its table. Two of the three common web shells, then, start disktide at sixteen colours, and nothing in the process could see it happening: Rich picks a colour system at startup and no terminal ever reports back.
- **so the depth is resolved from evidence, before Textual is imported** `viz/colordepth.py` answers in layers, each carrying its source: `DISKTIDE_COLOR_DEPTH`, `[ui] color_depth`, a `TEXTUAL_COLOR_SYSTEM` the user set (never overwritten -- someone who has reached for Textual's own knob has already decided), the clients attached to *this* tmux session, `COLORTERM`, `TERM`, then 256. `COLORTERM` sits *below* the client list rather than above it, which is not the obvious order and is the one that matters: it describes a process's environment and not a pane, so under tmux it is whatever the shell that started the server exported and it survives every detach -- one server read from a laptop and from a web shell, with `COLORTERM=truecolor` in the rc, would otherwise answer truecolor in the browser and hand tmux exactly the quantisation this is all about. It is consulted outside tmux, and inside it only when tmux could not be asked. The tmux layer is the one nothing else can do and the reason the rest exists: `TERM` inside tmux describes the pty, so the attached clients are the only place the truth is written down, and the *least capable* of them governs -- a session read from a laptop and a browser at once has to be legible in the browser. The answer is set on `TEXTUAL_COLOR_SYSTEM` at launch, which is a narrower window than it sounds: `textual.constants` reads that variable once at its own import, and `disktide.config` reaches Textual through `disktide.keys`, so even loading the config first is too late. The config layer therefore reads its one key out of the file with `tomllib` and nothing else, and three subprocess tests hold the ordering -- including one that asserts the failing order still fails, because that is the reason the function takes no argument. Driving the real TUI in a private tmux and reading the pane back with `capture-pane -e` is what caught this: the run that asked for truecolor was emitting `38;5`.
- **and sixteen colours get a theme designed for sixteen colours** Every route from sRGB down to sixteen goes through somebody's nearest-match, and the table above is what that costs. The sixth theme does not have one: it names its colours, and the terminal paints its own. Nine of the sixteen indices go on the marks that have to stay apart -- six categories, `other`, and two directory neutrals alternating by depth, where index 3 is the VGA brown so the inner rings read as the same tan the default paints them. Black is the background, bright white is text and selection, five are left for the inks and the chrome. The two markings the RGB path draws by interpolation become substitutions, because there is no 6 % of a name: a zebra-striped directory takes the neutral its own depth does not use, and a selected arc takes the one colour held back for it. The renderer still supersamples in RGB and has to -- the rim, the wedge walls and every separator are made of exactly that average -- so each fill goes in at its `STANDARD_PALETTE` coordinate and the cell folder snaps the result back, which means a covered cell comes out as the name it went in as and only the anti-aliased edges land between two. Doing that there rather than leaving it to Rich's downgrade is what makes the theme work at *any* depth: a truecolor terminal paints its own sixteen colours, not this table's. `muted` stopped being bare `dim`, and Textual's own `ansi-dark` needed one variable moved, because its block cursor is `ansi_white` and so is the `file` ink -- the invisible-text bug, reproduced exactly by the theme meant to fix it. The app renders with the theme whenever the resolved depth is 16, toasts once to say the terminal chose it, and leaves the saved theme alone; the picker offers it at any depth. `tool/palette_checks.py` carries both downgrade models (Rich to 256 then tmux 3.2a's table, and Rich straight to STANDARD), `gen_palette.py --check` prints 39/30/13/12, and the gates pin that every RGB theme still keeps eight distinct marks at 256, that the ANSI theme spends nine distinct indices and has a cursor row whose foreground is not its background, that nothing it emits is anything but a bare ANSI name, and the collapse itself as a number -- so a future palette that happens to fix any of it is noticed.
- **`disktide doctor` explains the picture instead of leaving you to guess** A new Colour block prints `TERM`, `COLORTERM`, `TEXTUAL_COLOR_SYSTEM`, the tmux clients attached to the session with their feature lists, the depth that was resolved and the layer that decided it, and -- only where a depth is below what the terminal can do -- the one line to change: the `terminal-features` string for a tmux client that reports no RGB, or `export COLORTERM=truecolor` for a web shell whose `TERM` is lying about it. A depth set by hand is never second-guessed. `doctor --json` gains a `colour` object with the same facts; schema version 6.
- **three web-shell frictions that only bite in a browser** `y` writes OSC 52, which is swallowed silently both by a tmux client whose terminfo has no `Ms` (`xterm-16color`, which is exactly what OnDemand hands out) and by an xterm.js built without the clipboard addon -- and there is no reply to read, so nothing can tell. The toast is the fallback now rather than a confirmation: it prints the path where it can be selected with the mouse and says so. Chrome takes F1 for help, F3 for find and F5 for reload, so the explorer's three chart keys are unreachable in precisely this environment; two alternatives already existed and neither was written down, so the key map says them on any screen that puts something on an F-key, and the guide's key table says them too. And the cell aspect: a web shell always lands on the assumed 2.0 and always will, because node-pty fills in no pixel winsize and xterm.js does not answer `CSI 14 t` either, so the guide says so rather than leaving a reader to work through the list.
- **and a fourth: every box on screen was drawn 1.2-1.8x too wide** The same Open OnDemand shell showed the welcome screen's Input, its Checkbox and both Buttons with their top and bottom border rows overhanging the text between them and their right edges scattered across three columns. The app's output was correct -- a tmux capture of the same screen at 307x71 lines up exactly -- and so was the terminal's cell grid. It was the font. xterm.js draws from the browser's monospace face and falls back to a proportional one for anything it does not carry, at that font's advance rather than at one cell; measured off the screenshot, a 72-cell Input drew its `▔` row 129 cells wide and its `▁` row 86 while its text row was the 72 it should have been. The glyphs missing are the eighth blocks and the quadrants, which is the part of the Block Elements range that is not in WGL4 -- and Textual's `tall`, `panel`, `hkey`, `vkey`, `wide`, `tab`, `inner` and `outer` borders are all built from them, which is where every torn box came from: `tall` on Input, Button, Checkbox, Switch and Select, `hkey` on Collapsible and the command palette, `vkey` on the footer's palette key, `outer` on toasts. Nothing in this codebase named one of them; they are Textual 8.2.8's defaults. App-level CSS now redraws all of them at the same geometry from the box-drawing block -- boxes become `solid`, the sides `hkey` reserved and drew blank stay `blank` -- so the chrome keeps its shape and its focus and variant colours without spending a glyph the browser cannot measure. `disktide.glyphs` holds the one copy of which glyphs and which border styles are allowed, `tests/test_web_glyphs.py` walks every screen in both colour modes and fails on a widget that resolves to an unsafe border, and `tool/capture_glyphs.py` drives the real app under tmux at 307x71 and 120x32 and reports any non-ASCII glyph on any pane that is not on the reviewed list.

- **the second half of that story: the block elements the browser *has* are drawn at the wrong size, so nothing DiskTide fills is a glyph any more** The first fix drew the line at WGL4 and declared the eight block elements Courier New carries -- `▀ ▄ █ ▌ ▐ ░ ▒ ▓` -- safe, on the argument that a font either has a glyph or it does not. Having the glyph was never the question. The next screenshot, an explorer in the same OnDemand shell at 307x71 and 8.28 px cells, measures every `░` in the tree's size bar at about 1.1 cells wide and 1.4 rows tall -- so each row's track bled over the size text of the rows above and below it, which is what "the green shade bars overlap" looked like -- and every `▀`/`▄` in the chart *narrower* than the cell, leaving a comb of background-coloured slits along every horizontal edge, with the rows carrying a long run of them shifted sideways by up to 0.6 cell (the chart's vertical seams measured at column 257.6 against 258.2). The advance is still one cell in both cases: it is the glyph's ink box, not the layout. Courier New is a typewriter face with an unusually light stroke and no fitting for a cell grid, and DiskTide cannot see the browser's font to know. So the rule is now the whole range: **nothing the app draws itself may be a block element (U+2580-U+259F); a fill is a background colour on spaces, and a ramp that needs height is ASCII.** In practice that is the tree's proportional bar (spaces under a new `bar_track` ink role, with a `render_label` override that re-applies the bar's background *after* Textual's cursor style, which is a later Rich span and would otherwise paint over it), the FS Overview's usage and capacity bars, the Settings theme swatches, the scan progress bar (a `Bar` renderable whose three glyphs are spaces and whose foreground styles become backgrounds -- subclassed, because the same renderable draws the tab underline where `━` is right), the mini trend sparkline (`.:-=+*#` instead of the eighth-block ramp, in every mode now), the `disktide scan` summary bar on stdout (`#`/`-`, because stdout is a pipe as often as a terminal), Textual's Checkbox and RadioButton (whose `▐X▌` sides are a half block doing a background's job), the Monitor's trend chart (plotext's default marker is its high-density set, `▀▄▖▗▘▚▝▞`, so the line is drawn with `dot` -- U+2022, which CP437 and Courier New both have -- at one dot per cell), and the `thick` and `block` border styles, which are built from `█▀▄` and which the app's panels and modals asked for. `double` is the heaviest box left and CP437 carries the whole double-line set, so it keeps the two weights `thick`-over-`solid` gave: a heavy frame around a panel, a light one around the widgets inside it. The `tiles` ring shape is the same fix in the chart: its vertical quantum was the framebuffer's half row, so every ring boundary that landed on one was drawn with `▀`/`▄`; it is a whole row now, the centre snaps to a row boundary, and a crisp shape's subsamples are all taken at the cell centre, so `_render_cells` emits nothing but spaces for it and the picture agrees with `hit_test` exactly. The cost is one ring-row at heights where the old rule got an odd number of half rows. `disc` and `fill` keep the half-block pass -- they are round, and a whole-cell circle is a staircase -- so the guide says to use `tiles`, which is the default, in a browser. There is still no setting. `ui.safe_rendering` is unchanged in behaviour and narrower in purpose: it is now the switch for a terminal that has no background colours to spend either.
- **the live chart was drawing the scan to a standstill** A home directory that the headless scanner walks in 36.8 s took about seven minutes in the TUI with the ring chart on: 323 s of the 420 s wall was the UI thread, against 10.7 s for the scheduler thread and about a second for each of the eight workers. The mechanism is not the frame rate: the scan service coalesces `NodeAggregateUpdated`, so the explorer is handed a new frame exactly as fast as it can paint one, and one frame at a 182x62 sunburst is 163 ms of pure Python. Every millisecond of that is spent holding the GIL, so each scan thread waited out a switch interval on every re-acquisition -- after each `stat`, each `scandir`, each future -- while the painter held it. More cores did not help and never could, which is why the `auto` gate's "at least four cores" clause is gone: it let exactly the biggest terminals through, and frame cost grows with cells. - **so the UI thread is on a budget now, and live snapshots are what it spends it on** `ExplorerScreen` stamps `thread_time()` and `monotonic()` on every snapshot it applies, and the next one waits until the CPU the thread has spent since then is back under an eighth of the wall clock that has passed. It is a closed loop rather than an estimate for a reason: the two obvious estimates were tried first and both were wrong. Timing `SunburstView._build_layout` misses the strip rendering and the tree panel entirely; timing from the snapshot to a `call_after_refresh` callback misses the *paint*, because the screen invokes its pending callbacks on idle whenever it believes nothing is dirty, and 24 of 38 samples in one scan came back at one to nine milliseconds for frames that then took 56-236 ms to build. A loop that only reads what the thread has already used cannot be wrong about any of it -- including a live chart whose arc count grows from 500 to 9,000 over a single scan, which is why the frame cost was never a constant to begin with. A skipped frame arms one timer for what is still owed and is replaced by the next, so a scan that goes quiet still lands its last picture, and the timer goes back through the gate rather than past it. Only the newest frame's changed list is applied, not the union of the skipped ones: the scheduler records a settled directory's whole ancestor chain on every publish, so the union adds nothing the next frame does not carry -- taking it anyway put 45,000 nodes into one `apply_live_update`, which sorts them all before discarding everything it cannot show. - **a third of the scan went into building nodes and a tenth into walking past them** 200,000 tiny files in 1,050 directories on warm local disk -- a tree `du -sb`, `ncdu` and `find -printf %s` all read in 0.3 s -- took disktide 2.2 s at one worker, and a GIL-holder profile put 30% of that in `FSNode.__init__`, 13% in `entry.stat`, 12% in `sum_available` and 10% in the post-walk tail. Three of the four are gone. `make_file_node` and `make_symlink_node` construct the node positionally (0.83 us against 1.12 us for the keyword form, once per file, and the symlink builder was calling `allocated_bytes_from_stat` twice for the same number). The two `sum_available((a, b))` calls per entry in the scheduler's hot loop are written out -- `None` propagates, everything else adds. And the tail stopped touching the leaves it has nothing to say about: `finalize_unique_allocated` sorted all 592k leaves of a home directory by path to order the hardlinked ones, which on an ordinary tree is none of them, so only `link_count > 1` leaves are collected and sorted now; `clone_tree(share_leaves=True)` no longer pushes every leaf onto its stack and into its clone map to hand back the original unchanged; and `FSNode.walk` stopped building a `reversed([])` for every leaf, four times a scan. 1.22x on that tree at one worker with the trees byte-identical, and positional construction makes the first 28 fields of `FSNode` a contract that `tests/test_tree.py` now pins.
- **wall time on a real home is set by the number of directories, not the number of files** A 700k-entry home directory in 88,147 directories -- seven entries each -- took 52 s over cold NFS at eight workers, 53 s at sixteen and 50 s at four. Wall time that does not move with worker count and 0.9 cores of user CPU is not a storage measurement; it is one Python thread doing about 250 us of bookkeeping per directory. On a home-shaped synthetic tree (982,847 entries, 88,000 directories, warm local disk, `du -sb` 1.84 s) that bookkeeping is now 1.47x cheaper at one worker (29.5 s to 20.1 s raw, 37.5 s to 25.5 s live) and 1.37-1.38x at eight (39.0 s to 28.5 s raw, 55.7 s to 40.3 s live), with live RSS down from 891 MB to 858 MB and the tree byte-identical. `_propagate` computes the aggregate delta once at the directory that changed and applies the same numbers at every ancestor, instead of building two ten-field contribution objects per level per directory; where the delta is all zeroes -- a streamed directory's result, whose chunks already carried every byte -- it relinks the direct parent and skips the walk entirely. `FSNode.shallow_copy` replaces the generic slots-dataclass copy (4.18 us to 1.27 us, and `copy.copy` still finds it), and the copy the worker made of every directory just to describe it is gone, because the fields the consumer reads are all written before the first entry is read. `_recalculate_directory` makes one pass over the child list where it made nine. A directory small enough to fit one entry chunk -- which at seven entries against a 256-entry chunk is almost all of them -- returns its entries in the result instead of paying a queue round trip, so the chunk queue, its lock and its `qsize` are back to serving the directories that actually need streaming. Futures announce themselves through a done-callback instead of being polled, which was 346k condition-lock acquisitions. Progress reports are rate-limited where they are built rather than where they are consumed (the engine already throttled at 0.1 s; below that a `SchedulerProgress` could never reach a display), with one unconditional report at the end so the final counts always land. And a live publish stopped copying 88,000 settled paths into a frozenset -- `build_live_view` only reads that set -- and now memoises the converted view of a settled directory, which by definition cannot change again.
- **a tree that changes while you scan it was reported as a tree you are not allowed to read** Scanning a directory that something else is writing to -- a build tree, a scratch area, a job's output -- turned a 4,000-file copy into a `partial` run with 13 phantom unreadable entries, one denied directory, two partial ones and three `AccessError` events reading "[Errno 2] No such file or directory". Nothing was denied; the entry was listed by its parent's `readdir` and gone by the time the `stat` reached it. `ENOENT`, `ESTALE` (its NFS form) and `ENOTDIR` are now their own thing: `FSNode` carries `vanished`, `vanished_count` and `vanished_subtree_count`, a directory that disappeared before its own job ran is marked `vanished` with `error` left at `None` and keeps its place in its parent's child list, and none of it reaches `inaccessible_count`, the progress error count, `AccessError` or the run's `partial` status -- the same churn now finishes `completed` with zero access errors and twelve vanished entries. Every other errno, `PermissionError` first among them, behaves exactly as it did, and a scan root that does not exist is still an error, because nothing listed it. The tree shows a removed directory as `(gone)` with no share bar, the details panel says "Removed during scan" and counts the entries that vanished below, and `scan` reports the count in both its text and its JSON (`coverage.vanished_entries`).
- **a directory 450 levels down was reported as a directory you are not allowed to read** A tree of 1,200 nested directories -- an unpacked archive, a build cache, a `node_modules` that grew a cycle -- stopped at level 442 with `[Errno 36] File name too long` recorded against it, which is the same badge a permissions failure gets: `du` and `find` walked all 1,200 and disktide said the rest was denied. The 4,096-byte cap is on the *pathname a syscall is handed*, not on the tree, so the walk stopped handing the kernel pathnames. Each directory is opened once, its own metadata comes from that descriptor, and every entry inside it is stat'd by name against it; the directory's own path is opened in 4,096-byte steps, four of them for a 10,900-byte path. The deep tree now reports 1,200 directories, one file and 4,096 bytes, with nothing denied. Cleanup and `readlink` still build a whole path and still fail past 4,096 bytes -- what is fixed is the scan.
- **and the same change made every scan cheaper** An `lstat` of a 202-character path is more work for the kernel than an `fstatat` of a 12-character name against a descriptor it already holds. One thread, no node building: 3.58 us per entry against 3.14 on warm local xfs, 13.0 against 11.0 on warm NFSv4. On the whole 980,560-entry benchmark tree at one worker that is 16.51 s down to 14.90 s, with system time down a third, 4.43 s to 3.02 s.
- **`allocated` counted every file in a tree and none of the directories holding them** A directory is a file too: it holds names and the filesystem charges it blocks for them -- 4 KiB for any directory at all on ext4, and on xfs once the names outgrow the inode, more again for a directory with thousands of them -- and `du` bills them. `st_blocks` was read for every file and symlink and thrown away for every directory, so a 300-directory tree with no files in it reported `allocated: 0` against `du -s --block-size=1`'s 12,288, and the 5,000-directory `make_homelike` fixture reported 0 against 7,376,896 -- on that tree every allocated byte *is* directory blocks. The number was already on the table: `scan_directory_once` `fstat`s the descriptor it opened the directory on, for the three scope questions it has to answer anyway. So `own_allocated_size` starts from `st_blocks * 512` instead of from zero, carried by the first entry chunk only -- `flush_chunk` zeroes the chunk accumulator, and the result node replaces whatever the chunks summed, so a streamed directory adds it exactly once and `scheduler_invariants` I7 fails if that stops being true. `accounting.finalize_unique_allocated` recovers the same blocks by subtraction, `own_allocated_size - sum(leaf.own_allocated_size)`, rather than re-stat'ing: only a leaf can be a second path to one inode, so nothing about a directory's blocks is ever deduplicated. Both totals now equal `du -s --block-size=1` exactly on the 5,000-directory tree -- 7,376,896 at `-w 1` and at `-w 8` -- and on a tree that *has* hardlinks `du` matches Unique rather than Allocated, because it dedupes by inode too. Logical is unchanged and now says so out loud: a directory's own `st_size` is 4,096 on ext4 whatever it holds and 24 on xfs for a directory holding two names, and neither number is payload anybody stored. Two consequences worth naming. Comparing a snapshot taken after this against one taken before shows a one-off rise of up to 4 KiB per directory in Allocated and Unique -- 4 KiB apiece on ext4, and on xfs only for the directories whose names outgrew the inode. And a parent's children no longer sum to the parent in those two metrics, short by the parent's own blocks -- which draws nothing new, because the sunburst and the treemap both normalise a ring by the sum of the children in it and never by the parent's value, exactly as they already had to for Logical, where the same gap is the parent's direct files.
- **and one directory you were not allowed to read blanked the whole scan's Allocated and Unique** `scan_directory_once` started every node at `allocated_size = own_allocated_size = None`, a denied directory returned before anything wrote a number back over them, and `_propagate` carries a `None` from any single node all the way to the scan root -- so one `chmod 000` directory anywhere under a home reported "Allocated: Unavailable" for the entire tree. The hedge lives where it already lived for Logical, in `inaccessible_subtree_count` and the `Coverage:` line. - **the scheduler stopped paying for a future per directory** A directory task is a call and a result. A `Future` also carries cancellation state, a condition variable and a callback list, and its round trip through `ThreadPoolExecutor` measured 15.6-20.8 us at one worker against 5.7 us for a plain queue handoff -- 88,000 times on a home-shaped tree, and 779k lock acquisitions in the profile of a single-worker scan. The benchmark tree at one worker went 15.28 s to 13.72 s on top of the descriptor change, 18.83 s to 13.72 s against where this release started. Threads no longer outlive the scan either, cancelled scans included -- the executor was shut down without waiting for them.
- **a mount whose metadata costs milliseconds was scanned as if it cost microseconds** Every network filesystem got eight workers, whatever it was: warm NFS, a CIFS share over a WAN, an object store behind FUSE. Wrapping `os.scandir` so every entry costs a fixed sleep and running the real scanner puts the knee where the latency does -- eight workers at 0.2 ms per entry, 32 at 1 ms, 64 at 5 ms, where the wall falls from 3.38 s to 0.88 s. - **inside a container, disktide believed it had the whole host** `sched_getaffinity` sees a cpuset and not a CPU *quota*, so under `docker run --cpus=1` on a 64-core box it planned for 64 CPUs, and `/proc/meminfo` is host-wide, so under `--memory=512m` on a 256 GB box it saw ~200 GB free and the "under 512 MB, scan serially" guard never fired. Both control-group hierarchies are read now, from the process's own group up to the root, tightest limit wins -- which is what a batch scheduler needs, because it sets the limit on the job and not on the task. A quota that binds makes the host an allocation, so host-wide load stops throttling a scan that is entitled to its slice. `disktide doctor` prints both under Platform: `CPUs: 16 available / 104 total (cgroup cpu quota: none)` and `Memory: 55917 MB available of 79296 MB (cgroup limit: 79296 MB)`.
- **a scan of a home directory holds 200 MB less** Twenty of the forty-one fields a tree node carries are meaningful only on a directory -- the child list, the four subtree diagnostics, the five scope flags, the three vanished counters, the sort cache -- and files are the tree: 892,560 of the 980,560 entries on the benchmark. Every one of them paid a slot for all twenty, plus a 56-byte empty list to hold the children it would never have. Files are now built as a slimmer `LeafNode` that `FSNode` extends, so a directory is exactly what it was and a file is 208 bytes of object graph instead of 424. Reads of the twenty are unchanged on a leaf -- they are class attributes holding the same defaults -- and a *write* raises, which is the point: a directory field set on a file would otherwise vanish silently from every total above it. The 980,560-entry benchmark at one worker went from 878 MB resident to 680 MB and 13.85 s to 11.89 s; 300,000 files in one directory went from 271 MB to 205 MB. Against where this release started: 877 MB and 16.98 s to 680 MB and 11.89 s.
- **every directory was applied twice, and almost every directory only happened once** A directory small enough to fit one 256-entry chunk does not stream: its children, its own bytes and the totals the worker already summed for it all come back together in one result. The scheduler applied that through both halves of the streaming protocol anyway -- an entry chunk built out of the result and pushed up every ancestor, then the result itself, recalculated over the same children, pushed up a second time with deltas that were by then all zero, recorded a second time, and settled. On the 88,000-directory fixture that is 88,000 of 88,000 directories, and the second pass was doing arithmetic whose answer was already on the node. One pass now, and the thread that does it went from **28.1 % of a raw scan's samples to 18.5 %** -- 31 us a directory to 17 -- which under one GIL is a second the walk gets back: a raw scan of the fixture at one worker goes **10.67 s to 9.42 s**, eight workers 19.97 to 18.08, a live scan 12.27 to 11.26, and the real explorer 10.63 s to 9.24 with the chart off and 13.21 to 11.60 with it on. The post-scan hardlink walk, which sorts and reconciles every path that shares an inode, now runs only when the scan actually saw a leaf with `st_nlink > 1`: `_recalculate_directory` is already the one loop over every child of every directory, so it answers the question on the way past and a tree with no shared inode gets its unique sizes copied from its allocated ones instead -- 368 ms to 114 on the fixture's tail, and byte-identical output on a tree that does have hardlinks. And a worker that finishes a directory stops taking the scheduler's event lock to raise a flag that is already up, which was 5 % of the worker thread at 88,000 directories. `tests/scheduler_invariants.py` gained the invariant the fast path rests on: every applied directory's twelve aggregates still have to equal a fresh sum over its children, checked on every result of every scan in the suite.
- **every bulk file generator in `tool/` now asks before it writes** `python tool/make_homelike.py --help` once read `--help` as its target and built 88,000 directories and 888,100 files into a directory of that name, on a quota'd NFS home, taking the account to 100 % of its inode limit. Argument parsing fixed that one script; it did not fix the shape. Every generator picked its own destination, several through `tempfile`, and `tempfile` follows `TMPDIR` -- which on an HPC account is routinely `~/tmp`. `tool/scratchguard.py` is the one gate they all go through now: it refuses a path under `$HOME` (`--allow-home` lifts it), a path on a network filesystem (`--allow-network`, decided by longest-prefix match against `/proc/mounts`, because `/users` is `autofs` and the `nfs4` that matters is mounted *under* it), and a path without inode headroom -- which no flag lifts, because being sure you want to write somewhere has never made room there. Headroom asks two sources and refuses if either one, when it answers, is short: `os.statvfs` reported orders of magnitude more free inodes on the home where the account had far fewer left, so `quota -w -u -p` is asked as well, and never fails closed on a host without the binary. With no path, the destination is `$DISKTIDE_SCRATCH` (or `$TMPDIR`) `/disktide-<user>/<label>`, through the same three checks. `make_homelike` plans the exact entry count before the first `mkdir` -- the build loop is pure RNG, so a planner walks the same sequence and counts without creating anything -- and hands the guard the real number rather than an estimate; the default plan is exactly 88,000 directories and 888,100 files, which is now a test. `python tool/scratchguard.py PATH --entries N` answers the same question from a shell, before running anything. The one path it does not argue with is a scratch root you configured yourself: with `$DISKTIDE_SCRATCH` set, a target under that root skips the *network* refusal, because the designated place for a large fixture on an HPC account is the site's scratch (`/fs/scratch/...` here, gpfs, no inode quota) -- a parallel filesystem, so it matches the fstype list, and a guard that refuses the one directory provided for the job only teaches people to pass `--allow-network` every time, which is the flag that would also have let a million files onto the home. Network only: a `$DISKTIDE_SCRATCH` under `$HOME` is refused like any other path, headroom is still checked, and the suite's own temp-root check trusts a `TMPDIR` under that root for the same reason.

- **the post-walk tail is where a big scan actually ends** On a 679k-node home directory the walk finished and the progress display sat frozen on `scanning` for seconds with an empty queue and no active workers, which reads as a hang. Four separate costs lived in that gap and all four are gone. `clone_tree` copied every node so final accounting could not mutate a published snapshot, but 592k of those 679k nodes are files and copying them dominated the stall at 10.7 s; the clone now takes `share_leaves=True` and copies only directories, because what the clone protects is a snapshot's *aggregates* and those live on directories -- the one thing `finalize_unique_allocated` writes to a leaf is that leaf's own final value, which is the right answer for the snapshot too. The provisional store still takes the full copy, since it hands the tree out for independent editing. `_emit_access_errors` sorted the entire walk by path to report a list that is usually empty, 0.66 s and 679k string comparisons on a scan that raised no access error at all; only the nodes with something to say are sorted now. And `ScanEngine` calls a new `walk_complete_callback` the moment the walk returns, so the phase moves to `FINALIZING` when finalisation *starts* rather than when it ends -- idempotent, because a collector that never calls it still gets the phase set on return, and `_PRE_SCAN_PHASES` keeps the collector's last progress report from bouncing the phase back to `SCANNING` and flickering every display at the worst possible moment.
- **the category rollup runs on live frames without eating a core** Directory tints came from a rollup that is one pass over every node, so it could not run per live frame and did not run at all until the scan finished -- the finished scan then painted one wholly neutral frame and recoloured a few hundred milliseconds later, which reads as a second jump. The pass is now thrown at a worker whenever it has been idle for eight times its own last duration: on a small tree that is almost every frame, on a large one it settles to a few seconds apart, and either way the cost is a fixed fraction of one core however big the scan gets. Its own guard flag, not `exclusive`, is what keeps two passes off the CPU at once, because a thread worker cannot actually be interrupted. The live-frame path also stopped rebuilding the bounded view the scheduler already shipped on the event; it rebuilds only when the tree has since been switched to a metric other than the one the run was started with.
- **and it stopped rendering the scan tree into a string first** Textual builds a worker's debug description by `repr()`-ing every positional argument unless it is handed one. `FSNode` is a plain dataclass whose children are in its repr, so the rollup worker rendered the entire scan tree into a string before it started -- 5.3 s and half a gigabyte on that same home directory, on the UI thread. Every `@work` that takes a node now passes `description=`.
- **a live scan could take the treemap down on nearly every frame** An in-flight scan lays out `LiveViewNode`s, which carry the measurements a chart draws with and none of the four subtree diagnostic counters an `FSNode` has, and `_aggregate_node` built an unconditional `FSNode` for its "… N more" stand-in -- so every fold path read attributes that were simply not on the object and raised inside `render_content_line`. The stand-in is now the same shape as the siblings it replaces, `LiveViewNode` grew the `depth` field the synthetic path is spelled from, and `viz/layout.py` names the union it was always handed as `LayoutNode`.
- **quitting on an exception no longer leaves the scan running** The TUI's teardown -- cancel the scan, close SQLite -- ran after `app.run()` returned, and `app.run()` also *raises*: Textual re-raises whatever took the TUI down, and on that path nothing below it ran. The scan then outlived the app that started it, and because Textual's thread workers live in the default executor, which the interpreter joins on the way out, the process sat at a dead terminal for as long as the walk had left (~50 s on a home directory) before the traceback was even printed. In a `finally` now, which turns that into the walker's usual ~10 ms bail.
- **a space-time context from the previous scan cannot land on the new one** Nothing requests a context during a scan, so one arriving mid-scan was asked for by the *previous* scan's completion, after which the user pressed `i`, `u` or `r`. Letting it through ran `_apply_visual_mode`, which reloads the size tree and repaints the chart from the finished root -- on top of the live stream, which then patched the old tree with the new scan's partial nodes. It is dropped; the new scan's own completion asks again, for the tree it actually produced.
- **the settings picker fits its longest option** "Colorblind-safe" is fifteen cells and a `Select` spends eight on border, padding and the arrow when closed and six in its open overlay, so at a 20-cell width the option wrapped onto a second line, grew the control out of its three-cell row and shunted the swatches beside it. The picker is 23 and the label column 27 -- the three columns of a row share the 70 cells an 80-column terminal leaves inside `.setting-row`, so a cell the label does not need is one the picker does. The hint beside it names the pip extra `[watch]`, and a `Label` reads its text as content markup, so the brackets parsed as a style tag and the hint rendered as "( extra on Linux)"; it is `markup=False`.

- **the suite can now be shaped like the host it fails on** Three of the four divergences that have turned the board red were a test reading the host rather than reading disktide: the order `os.scandir` returns entries in (an NFS home gives creation order, ext4 gives hash order), a mount whose rotational bit is unreadable, and the core count -- which is an *input to product behaviour*, since the `live_scan_render` auto-gate turns live rendering off below four cores and sends the explorer down a different path on a two-core runner. Neither `taskset` nor a container's `--cpus` reproduces that; both leave `os.cpu_count()` reporting the host's count. `tests/hostshape.py` models each axis as a deterministic caricature, `DISKTIDE_HOST_SHAPE=readdir,medium,cores` turns them on, and the header line names the active shapes so a red log explains itself. **Category colors that survive theme and colorblindness, dominance-tinted directories, and the return of the mouse**

## v0.2.22

**A sunburst that is actually a circle, painted with anti-aliased half-blocks**

- **cell aspect** Every chart assumed a character cell was exactly twice as tall as it is wide, because that is the only ratio at which a braille dot is square. Real cells are not: a 14px monospace face at 1.2 line height gives 7x17 pixels, a ratio of 2.43, and drawing a circle as if it were 2.0 stretched the disc vertically by 21%. The sunburst was a visible ellipse. Most terminals report the pane's pixel size next to its cell size in `TIOCGWINSZ` -- tmux forwards it to every pty it owns -- so the ratio is now measured rather than assumed, and the disc comes out round on any font. `DISKTIDE_CELL_ASPECT=2.43` overrides the measurement; a terminal that reports no pixel size still gets the old 2.0.
- **half-block renderer** The braille layer is gone. A braille dot is on or off, so a partially covered cell could only be stippled, and against the solid interiors the dotted rim -- and much worse, the dotted walls of every empty wedge, which cut clean through the disc wherever a leaf has no children -- read as dirty plumes rather than edges. The disc is now supersampled into a framebuffer of half-cells, four subsamples each, and every cell resolves to a space over one color or to `▀`/`▄` over two. Rims, wedge walls, and separators all come out as coverage blends. A half-covered cell draws its block as *foreground only*, so the widget's own background shows through and no background estimate can halo the disc. Uniform samples average back to themselves exactly, so ring interiors stay perfectly flat. The whole compute-and-render pass came out about 1.4x faster than the braille path at every pane size.
- **separators** Sibling directories at one depth were given the identical color -- hue and saturation from the scheme, luminance from depth alone -- with nothing drawn between arcs or between rings, so a run of them merged into one undivided blob. Each ring now carries a hairline of its own darkened color just inside its outer edge, and each boundary between siblings carries one along its length, skipped wherever a neighbour is too narrow to survive it. Both are narrower than the subsample spacing, so each subsample mixes by the fraction of its footprint the seam covers; that conserves the seam's ink and resolves it as an even line instead of a dashed one. Sibling directories also alternate slightly in luminance, which carries the division through the arcs too small for a seam.
- **treemap squareness** `compute_layout` squarified in doubled-height space with the factor 2 hard-coded, which is the same wrong assumption in the other chart. It now takes the measured cell aspect, so a block that squarify believes is square is square on the viewer's screen. Callers that pass nothing still get 2.0.
- **drawille** Dropped from the dependencies along with `viz/braille.py`; nothing imports it any more.

## v0.2.21

**Legible visualizations: a solid sunburst with a braille rim, a treemap without slivers**

- **sunburst fill** The ring chart drew every interior cell as a fully-lit braille glyph over a darkened copy of the arc color. Terminal fonts leave gaps between braille dots and between text lines, so that background bled through everywhere and the disc read as a halftone dot grid with horizontal banding -- the "noise" in the chart was the medium, not missing data. A cell whose whole 2x4 dot block belongs to an arc is now painted as a solid block of the arc's own color, undarkened.
- **sunburst rim** Filling an arc set a full-cell background for every dot the stroke touched, so a cell the circle merely clipped still got a whole dark chip and the silhouette was quantized to character cells. Partially covered cells now render the braille glyph alone, with no background, and the edge resolves at 2x4 sub-cell steps against the terminal's own background instead of a staircase halo.
- **sunburst rasterizer** Arcs were filled by stroking concentric integer-radius circles and truncating each sample to a pixel, which wrote some dots many times over and never reached others. The disc is now scan-converted once: a pixel's radius picks the ring and its angle picks the arc by binary search over that ring's intervals. Every covered dot is set exactly once, and the whole compute-and-render pass came out about 1.7x faster at every pane size.
- **sunburst cracks** Arcs spanning under half a degree were discarded *before* being recorded, so nothing owned their slice of the ring and the fill left a hairline of unpainted dots running through it. Such an arc is now emitted -- it simply stops there instead of subdividing further -- and rasterizes as its own hairline of color.
- **treemap aspect** The layout squarified in raw cell units, but a terminal cell is about twice as tall as it is wide, so it was optimizing squareness the viewer never sees; with one dominant sibling the remainder landed in a thin full-height strip. Squarify now runs in doubled-height space and the result is mapped back to cells, so blocks are square on screen and crumb strips fall out as horizontal rows a label fits in.
- **treemap slivers** Nothing consolidated entries too small to draw: `bounded_children` aggregates only past a *count* cap, so a dozen sub-cell siblings each still demanded a rect that the integer snap inflated to the one-cell minimum -- several onto the same cell, where whichever was drawn last erased the rest. Runs of siblings that cannot render are folded into a single labeled "… N more" block, before layout when they are individually sub-cell and after it for strips too thin to carry a label. A child on the selected path is never folded away.
- **treemap overlaps** Inflating a zero-size rect to the minimum moved a boundary its neighbor did not know about; both claimed the cell, and when the neighbor was a *parent* rect an entire subtree was repainted out of existence. The inflated rect now takes the cell from its neighbor rather than drawing on top of it, and endpoints are snapped in coordinates local to the parent so a boundary two rects reach by different arithmetic still lands on one integer.
- **anti-fragmentation invariant** The pattern suite now asserts that every leaf rect owns essentially every cell it covers -- losing at most a single row or column to a neighbor's snap -- and that no rect with area is rendered nowhere. The suite's old demand that at least ten of a hundred sub-cell files each get their own rect was the requirement that produced the overlaps; it now asserts that every child is represented, individually or by an aggregate that accounts for it.
- **area still means size** Nothing small was inflated to make it visible: rectangle area and arc angle continue to encode the selected metric exactly, per ADR 0006. Consolidation changes only what carries the label -- an aggregate block reports the combined size of everything it stands for.

## v0.2.20

**CLI conventions: silent quit, stream discipline, discoverable subcommands**

- **silent quit** Quitting the TUI no longer prints `Exiting...` or `DiskTide closed. Goodbye!`. Both dated from the era when teardown took tens of seconds and the user needed telling that the process was still working; since the `os._exit(0)` shutdown landed in v0.1.6 the whole exit is ~200 ms, so the messages were noise scrolled into the user's shell history. A terminal program that exits successfully says nothing -- `htop`, `ncdu`, `less`, and `vim` all return you to the prompt in silence. The only bytes written after the TUI tears down are now the terminal-restore escapes.
- **scan streams** `disktide scan` wrote its progress counter to stdout without checking for a terminal, so `disktide scan / > report.txt` captured `\r`-separated redraw frames inside the report. Run narration -- queue position, start banner, phase changes, worker selection -- now goes to stderr with the rest of the status, stdout carries the report alone, and the carriage-returned counter is drawn only when stderr is a terminal.
- **scan --json** Added machine-readable scan output, matching `doctor`, `cleanup`, `monitor`, and `alerts`. The document is versioned and carries the run id, status, policy, worker selection, all three byte totals, coverage counts, and the root's direct child directories sorted by the selected metric. A cancelled or failed run still emits a parseable document alongside its non-zero exit code.
- **cleanup --json** `disktide cleanup PATH --json` prefixed its document with `Scanning ... for cleanup targets...` on stdout, and answered `No cleanup targets found.` in plain text, so neither case parsed. The notice moved to stderr and the empty case now returns a document.
- **cleanup subcommands** `cleanup` was one flat command that hand-dispatched `rules`, `history`, `undo`, `purge`, and `quarantine` out of an `UNPROCESSED` argument tuple, so `disktide cleanup rules --help` printed the parent help and no subcommand appeared in any help output. An option that takes a value has to follow its subcommand (`cleanup history --by category`): the router cannot know an option's arity before it has picked the command, so it stops at the first bare token rather than risk routing an option's value as a subcommand name.
- **watch exit code** Ctrl-C out of `disktide watch` printed to stdout and exited `0`, so a caller could not distinguish an interrupt from a host that reached `--max-time`. It now reports on stderr and exits `130`, matching what `scan` already did.
- **TUI without a terminal** `disktide` with stdin or stdout redirected sat forever waiting on a keypress that a pipe can never deliver. It now fails immediately with an explicit message and exit `1`, pointing at the subcommands for non-interactive use.
- **help text** Three docstrings doing double duty as Sphinx source rendered their ``literal`` markup verbatim in `--help`; the top-level docstring lost its line breaks to Click's paragraph rewrapping. Both are fixed.

Since `e174a6a` (v0.1.6 release).

**Branding**

- **change** The product and canonical executable are now named `fsmonitor`. The Python distribution and legacy `fsmonitor-cli` executable remain available for package-index and command compatibility, and the existing XDG config/data directories are retained so settings and snapshot history survive the rename.

**Explorer**

- **fix** The tree's quantitative sort now follows the active bar metric. With the bar toggled to file count (`t`), directories were still ordered by bytes; the default sort now orders by the active metric (count or size), matching what the treemap and sunburst already do, and toggling the metric re-sorts the tree. Name and modified-time sorts remain metric-independent. The sort indicator reflects this (`Sort: Files` when sorting by the count metric).

The tree is `display: none` during a scan, so it loses focus; nothing restored it afterward, leaving arrow keys controlling whatever grabbed focus while it was hidden. The explorer now refocuses the tree once the scan completes, and a reload pins the cursor to the root so it's always live and visible.

**FS Overview**

- **feat** The single **Speed** column is replaced by a **Storage** column of facet badges that break the conflated speed heuristic into orthogonal physical properties. The first badge is the *medium* (`Flash` / `HDD` / `RAM` / `Network` / `?`); it is followed by any detected *transforms* — `RAID` (md device), `Encrypted` (dm-crypt, via a `CRYPT-*` sysfs uuid), `CoW` (btrfs/zfs), and `Compressed` (a `compress=` mount option) — each materially shifting the performance profile yet invisible to the flash-vs-HDD axis. Transforms are detected once at load with no extra I/O. The detail modal gains a matching **Attributes** row. The medium badge already encodes locality, so a network mount shows `Network` with no redundant `Local` badge. The classifier (`sysinfo.storage_class`) is now the single source of truth shared by every view, and newly recognises RAM-backed filesystems (`tmpfs`/`ramfs`), which previously fell through to "Unknown".
- **feat** New opt-in **Benchmark mount** action (`b`): an on-demand throughput probe of the highlighted mount, since the storage-class badges are only heuristics. Because it writes a temporary file, it is gated behind a confirm prompt (press `b` again, muscle-memory friendly) so a stray keystroke never starts disk I/O. The probe atomically creates a unique mode-0600 temp file, writes ≤256 MiB (strictly capped at 25% of free space and refused when less than 1 MiB is safe), `fsync`s, drops the page cache via `posix_fadvise(DONTNEED)`, and reads back cold — reporting buffered-write and approximate cold-read bandwidth without root. The result is recorded per mount for the life of the screen and shown as a **Measured** row when that row is reopened. New module: `scanner/benchmark.py`.
- **fix** "Used" and "Usage %" no longer over-report by the root-reserved block count. The screen computed `used = total - f_bavail`, which folds the unprivileged-user reservation (the default ~5% on ext4) into used space — on a typical root filesystem this nearly doubled the reported usage versus `df` (e.g. 11.4% shown vs 7% real, a 48 GB overstatement). It now follows `df` semantics exactly: `used = (f_blocks - f_bfree) * f_frsize`, `free = f_bavail * f_frsize`, and `usage_pct = used / (used + free)`. The reclaimed gap is exposed as a new **Reserved** row in the per-filesystem detail modal.
- **fix** The aggregate summary (Total / Used / proportional bar) no longer double-counts capacity for devices mounted at more than one path. Bind mounts and btrfs subvolumes report the full pool size from each `statvfs`, so summing raw mount entries inflated the totals; the summary now de-duplicates by backing device first, and its percentage uses the same `used / (used + available)` denominator as the per-mount rows. The per-mount table still lists every mountpoint.
- **fix** A stale NFS/CIFS mount can no longer wedge the loader on the spinner forever. `statvfs` on network filesystems now runs under a 3 s watchdog (local filesystems, which never block, are stat'd directly) and a timed-out mount is skipped.
- **fix** Non-ASCII mountpoints are no longer mojibaked. `/proc/mounts` octal escapes (`\040` etc.) were decoded with `encode('utf-8').decode('unicode_escape')`, which reinterpreted UTF-8 bytes as Latin-1 (`/mnt/café` → `/mnt/cafÃ©`). A targeted octal-only unescape (`unescape_mount_path`) replaces it, shared across `sysinfo` and the overview screen.
- **fix** The usage bar clamps over-100% values (the `*` over-quota case) instead of emitting an over-length bar with a negative empty count.
- **fix** Refreshing (`r`) is now `exclusive`, so mashing the key can't stack overlapping loader threads.

**Block Devices**

- **feat** The FS Overview gains a second **Block Devices** panel that enumerates the whole block layer via `lsblk -J -b`, surfacing storage that `/proc/mounts` + `statvfs` fundamentally cannot see: unmounted-but-formatted filesystems, unformatted partitions, and raw disks with no detected filesystem or child device. Each disk is shown with its partition tree and a colour-coded status (`● mounted`, `○ not mounted`, `○ unformatted`, `○ raw / no filesystem`); the panel header reports disks with no mounted filesystem and their total capacity without implying the contents are safe to reclaim. - **fix** Quit no longer hangs the shell for tens of seconds after a large scan. Worker threads are doing read-only FS scans, so killing them mid-syscall is safe; the kernel reclaims the entire FSNode tree's memory in microseconds vs the seconds Python takes to do it with refcounts and finalizers. ## v0.1.5

Since `6cb0459` (v0.1.4 release).

**Scanner**

- **fix** Symlink scanning is now one syscall per entry. The walker previously did three (`entry.stat` for the link, `os.readlink` for the target text, `os.stat` to follow the link); on slow shared storage with many symlinks each extra syscall is a server round-trip, blowing up scan times by an order of magnitude. `os.readlink` and the target-following `os.stat` are now deferred to `classify_symlink`, called on demand by the Details panel and the `i` action; the result is cached on the node. Measured on one cluster home (6.1M files, 100 GB on NFS): 2386 s on the pre-fix build, 195 s after, a ~12x recovery and ~20% under the v0.1.3 baseline.
- **feat** On top of that, the engine eagerly classifies the first 100 symlinks it sees at the scan root so a typical `fsmonitor ~` still shows `→ /target` arrows for the handful of links at home root. The cap is hard, so it cannot regress the case where the scan root itself contains hundreds of thousands of symlinks.
- **fix** Directory scans no longer recurse forever on a filesystem cycle. A bind mount or other setup that makes a directory reappear inside itself used to send the scan into an infinite loop; the walker now tracks each directory's `(st_dev, st_ino)` identity along the path from the scan root and stops when a directory is its own ancestor, marking it `(loop)` in the tree and the Details panel. Symlink loops were already prevented; this closes the non-symlink case.

**Progress**

- **fix** Scan progress now updates continuously during a deep scan instead of freezing while a single big subtree is being walked. The walker calls a per-directory tick callback as each directory finishes; the engine folds those into shared live counters and forwards them through the existing `ProgressThrottle` (100 ms coalesce). The earlier behavior only updated when an entire top-level subtree completed, so a scan with one dominant child sat with frozen `Dirs / Files / Size` counters for minutes.
- **fix** The scanning overlay's progress bar is now indeterminate (a pulsing animation with no percentage). The earlier percentage was `completed_top_level_dirs / total_top_level_dirs`, unrelated to actual work, and routinely parked at 97% while one large subtree finished. Without a pre-count pass there is no honest progress fraction; an indeterminate bar plus the now-continuously-moving counters is the honest feedback.

**Tooling**

- **feat** Two diagnostic scripts under `tool/`. `tool/bench_scan.py` is a version-agnostic one-shot that prints `wall-time / dirs / files / size / rate` for any scan path and any prior release (uses only `ScanEngine().scan()`). `tool/diag_scan.py` adds a 1-second heartbeat (with stall detection), a per-directory hotspot table, and an optional `--profile` pass that wraps the scan in `cProfile` and dumps the top callees. Both accept `--workers N` to isolate threading from the picture. These are how the symlink regression above was diagnosed; see [docs/blogs/2026-05-23-symlink-scan-nfs-speedup.md](blogs/2026-05-23-symlink-scan-nfs-speedup.md).
- **add** `tests/test_tools.py` smoke-tests both scripts as subprocesses against a real `tmp_path` and asserts the documented output shape. The scripts also degrade gracefully if the scanner's internal API changes (defensive `getattr` on every field, the diag's monkey-patch wrapped in `try/except` with a stderr notice on failure), so they keep working across releases.

- **docs** Architecture guide, filesystem-call reference, and contributing guide updated for the deferred-symlink-classification behavior and the two new diagnostic scripts.
- **docs** New blog post under `docs/blogs/` walking through the symlink-scan regression hunt end to end: cProfile-driven diagnosis, the fix, measured 12x recovery, and the small UX trade-offs the lazy scheme accepts.

- **fix** Pressing `q` on a large scan no longer hangs the shell for many seconds. The walker now propagates the engine's cancel event through every recursive call, so worker threads bail out within ~10 ms instead of running the in-flight subtree to completion.
